4. Phase 1 — Data Modeling & Schema Design (20 marks)
Design the database around EV charging operations. The following are recommended core entities; refine fields and relationships during modeling, document the final decision, and then keep that schema unchanged in later phases.
Entity
Purpose
Example key fields
User / EVOwner
Customer account and access
user_id PK, full_name, email UNIQUE, phone, password_hash, role, status
Vehicle
Vehicles owned/used by customers
vehicle_id PK, user_id FK, registration_no UNIQUE, make, model, battery_capacity_kwh
Station
Charging location and operating details
station_id PK, name, address, city, opening_hours, status
ChargingPoint
Individual EV charger at a station
point_id PK, station_id FK, connector_type, max_power_kw, status
Booking
Reservation of a point/time slot
booking_id PK, user_id FK, vehicle_id FK, point_id FK, start_at, end_at, status
ChargingSession
Actual charging event and energy usage
session_id PK, booking_id FK nullable if walk-in is allowed, user_id FK, vehicle_id FK, point_id FK, start_at, end_at, energy_kwh, unit_rate, total_cost, status
Payment
Simulated payment for a session
payment_id PK, session_id FK, amount, method, status, transaction_reference UNIQUE, paid_at
Modeling and normalization requirements
Create an ER diagram with cardinalities (1:1, 1:M, M:N as applicable) and explain the relationships, optionality, and business rules.
Provide the final relational schema with primary keys, foreign keys, UNIQUE constraints, CHECK constraints, NOT NULL constraints, and indexes where appropriate.
Explain 1NF, 2NF, and 3NF for the final design. Avoid storing derivable or duplicated data without a documented historical/audit reason.
Define how bookings prevent overlapping reservations for the same charging point, how charger status changes during a session, and whether walk-in sessions are supported.
Define the billing rule clearly, for example total_cost = energy_kwh × unit_rate, with any session fee/tax represented explicitly if included.
Use consistent date/time handling, status values, currency precision, and naming conventions.
Deliverables: docs/er_diagram.mmd, docs/schema_and_3nf.md, database/01_schema.sql.
5. Phase 2 — Procedural SQL Implementation (20 marks)
Implement the approved Phase 1 schema using DDL.
Create stored procedures/functions to calculate session charges, create/complete a charging session, and record a simulated payment or refund state where relevant.
Create triggers or equivalent database-level logic to validate session data, reject invalid end times, prevent invalid energy/cost values, and enforce required charger/session status transitions where feasible.
Prevent overlapping confirmed bookings for the same charging point and time window. Use transaction-safe logic and explain any concurrency limitation of the chosen approach.
Insert realistic synthetic data: at least 10 customer accounts/EV owners, multiple vehicles, at least 3 stations with multiple charging points, bookings, sessions, and payments spanning at least three months.
Include valid and invalid examples such as completed, cancelled, pending, occupied, unavailable, and failed-payment states.
Make seed scripts repeatable or document a safe database reset procedure.
Deliverables: database/02_routines_triggers.sql, database/03_seed_data.sql, and documentation of charging/billing assumptions.
6. Phase 3 — Queries, Reports, Indexing (20 marks)
Build reports using the same seeded database:
Station utilization report: charging hours or occupied time versus available time, with assumptions clearly defined.
Charging history per EV owner, including date, station, point, energy consumed, rate, total cost, and session status.
Revenue report by station and month, based only on the defined successful payment/session statuses.
Charger availability/status report and booking schedule for a selected station/date.
High-usage report: energy delivered by station, charger, or month.
Add justified indexes to columns used in joins, filters, and sorting. Consider composite indexes based on real query predicates.
Capture EXPLAIN output for at least one report before and after an index. Record query, index, plan, and observed difference. Use EXPLAIN ANALYZE only when supported by the installed database version.
If the optimizer chooses the same plan or the data is too small to show improvement, state that honestly and use a larger synthetic dataset where appropriate.
Deliverables: database/04_reports.sql, database/05_indexes.sql, docs/query_plan_comparison.md.
7. Phase 4 — Security, Access Control & Testing (20 marks)
Implement at least these roles:
Admin/Station Operator: manage stations and charging points, view all bookings/sessions, change point status, manage tariffs, and review reports.
EV Owner: browse available stations/points, create and cancel eligible bookings, view own vehicles, own charging sessions, and own payment history only.
Enforce authorization on the server for every protected route. Determine the owner from the authenticated session, not a client-supplied user_id. Prevent access by changing URL or request parameters.
Hash passwords, store secrets in environment variables, use safe sessions, and never expose SQL credentials or stack traces.
Use least-privilege database roles/users where practical. If the application uses a shared DB account, document the server-side access controls and provide appropriate SQL grant examples.
Wrap booking confirmation, session completion, charger state changes, and payment recording in transactions where multiple writes must succeed together. Roll back on errors.
Test: duplicate/overlapping booking, booking end before start, booking a disabled point, negative energy, negative tariff, session end before start, payment failure, duplicate transaction reference, unauthorized access to another owner's data, and rollback after a forced failure.
Document each test with test ID, scenario, setup, expected result, actual result, pass/fail, and evidence.
Deliverables: database/06_roles_permissions.sql where applicable, automated tests, docs/test_cases.md, and transaction demonstration evidence.
8. Phase 5 — Integration, UI & Final Presentation (20 marks)
Build a single connected web application using the approved schema and database logic. Required flows:
Login/logout and role-specific dashboards.
Admin: create/edit stations and charging points, configure tariffs, view bookings/sessions, and generate reports.
EV Owner: view stations and charger availability, register/manage vehicles, book or cancel a slot subject to rules, and view personal charging history and payments.
Session workflow: simulate start/stop charging, calculate energy/cost, update point availability safely, and record simulated payment status.
Report pages for station utilization, monthly revenue, charging history, and charger status.
Show clear validation errors, empty states, confirmation prompts, and safe failure handling. Do not expose controls that the current role cannot use, and enforce authorization on the server regardless.
Use consistent navigation and responsive layouts. Prioritize reliability and DBMS demonstration over decorative complexity.
