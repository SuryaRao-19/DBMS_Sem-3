## 1. Objective

To demonstrate and measure the concrete impact of secondary B-Tree indexing on query execution plans in MySQL 8.0+. We evaluate execution plans generated by the MySQL Query Optimizer using `EXPLAIN` before and after introducing composite secondary indexes.

---

## 2. Test Case: Monthly Revenue & Settlement Query

### 2.1 The Target SQL Query
This query filters successful transactions across a designated reporting period (spanning the synthetic three-month window):

```sql
SELECT 
    payment_id, 
    session_id, 
    transaction_reference, 
    amount, 
    payment_method, 
    paid_at
FROM Payments
WHERE payment_status = 'SUCCESS' 
  AND paid_at >= '2026-08-01 00:00:00';
```

---

## 3. Execution Plan Comparison

### 3.1 Initial Execution Plan (Without Index)
*Condition: Index `idx_payment_status_date` dropped from table `Payments`.*

```sql
EXPLAIN SELECT payment_id, session_id, transaction_reference, amount, payment_method, paid_at
FROM Payments
WHERE payment_status = 'SUCCESS' AND paid_at >= '2026-08-01 00:00:00';
```

#### Actual MySQL 8.0 EXPLAIN Output:
| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | SIMPLE | Payments | NULL | **ALL** | **NULL** | **NULL** | NULL | NULL | 6 | **16.67** | Using where |

#### Interpretation:
- **Access Type (`ALL`):** The optimizer is forced to perform a **Full Table Scan**, examining every data page sequentially in the clustered index.
- **Possible Keys:** `NULL`, indicating that no index could be leveraged for the `payment_status` or `paid_at` predicates.
- **Filtered (16.67%):** The storage engine reads all rows and passes them to the SQL layer, which evaluates the `WHERE` condition row-by-row and discards non-matching rows.
- **Extra (`Using where`):** Row qualification occurs after disk read, increasing CPU utilization.

---

### 3.2 Index Addition & Optimization Strategy

To optimize this high-frequency analytical access path, we constructed a **Composite Multi-Column B-Tree Index**:

```sql
ALTER TABLE Payments ADD INDEX idx_payment_status_date (payment_status, paid_at);
```

#### Column Order Rationale:
1. **Equality Column First:** `payment_status` has an exact match predicate (`= 'SUCCESS'`), which narrows the search space to a specific subtree in the B-Tree.
2. **Range Column Second:** `paid_at` has an inequality range predicate (`>= '2026-08-01'`), allowing an efficient continuous range scan across leaf nodes.
3. **Key Length:** `payment_status` is an `ENUM('PENDING', 'SUCCESS', 'FAILED', 'REFUNDED')` (1 byte internal) + 1 byte NULL indicator + `DATETIME` (5 bytes) = **7 bytes** total `key_len`.

---

### 3.3 Optimized Execution Plan (With Index)
*Condition: Index `idx_payment_status_date` applied.*

```sql
EXPLAIN SELECT payment_id, session_id, transaction_reference, amount, payment_method, paid_at
FROM Payments
WHERE payment_status = 'SUCCESS' AND paid_at >= '2026-08-01 00:00:00';
```

#### Actual MySQL 8.0 EXPLAIN Output:
| id | select_type | table | partitions | type | possible_keys | key | key_len | ref | rows | filtered | Extra |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | SIMPLE | Payments | NULL | **range** | idx_payment_status_date | **idx_payment_status_date** | **7** | NULL | 6 | **100.00** | Using index condition |

---

## 4. Analytical Findings

| Metric | Before Index | After Index | Improvement / Impact |
|---|---|---|---|
| **Access Method (`type`)** | `ALL` (Full Table Scan) | `range` (Index Range Scan) | Transitions from $O(N)$ sequential scan to $O(\log N + K)$ B-Tree traversal. |
| **Index Utilized (`key`)** | None (`NULL`) | `idx_payment_status_date` | Query engine directly accesses the target leaf nodes. |
| **Filtered Percentage** | `16.67%` | `100.00%` | 100% of rows read from the index condition satisfy the predicate. |
| **Engine Pushdown (`Extra`)** | `Using where` | `Using index condition` | **Index Condition Pushdown (ICP)** active: filtering occurs inside the InnoDB storage engine before returning rows to MySQL server layer. |

### Limitations & Dataset Size Discussion
In our synthetic academic demo dataset (6 payments, 6 sessions), both queries execute in sub-millisecond time due to MySQL buffer pool caching. However, at production scale (e.g., $1,000,000$ payment records):
- An `ALL` scan would read $\approx 50,000$ pages ($\approx 800\text{ MB}$) from disk.
- The `range` scan traverses the root-to-leaf B-Tree in $3$ to $4$ page reads ($\approx 48\text{ KB}$), achieving a $\sim 10,000\times$ I/O reduction.
